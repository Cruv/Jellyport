# Emby to Jellyfin migration capabilities

Jellyport migrates user records through the servers' authenticated APIs, optionally reading source history from an encrypted local database projection. Both servers must already contain the media. It does not copy media files or install an Emby database into Jellyfin. Exact usernames are the default; an administrator-approved identity mapping can associate accounts with different names.

Migration transfers **played / unplayed flags only** and preserves existing Jellyfin activity. Emby's unplayed flag never erases a Jellyfin played flag. Confident matching is required; missing and ambiguous media are reported instead of guessed. Existing Jellyfin passwords, permission policies, preferences and personal data remain intact. New accounts receive a generated password and the configured default Jellyfin account role, or the legacy Jellyfin template when no default role is selected.

## Played-state migration

A played, supported playable item in Emby marks its confidently matched Jellyfin item played. A destination item already played needs no update. Unmatched or ambiguous items are skipped and reported; untouched items on a fresh account retain Jellyfin's unplayed default. Supported playable types are movies, episodes, audio, music videos, videos, books, audiobooks and trailers. Series and season identity can help match episodes, but their aggregate completion flags are not copied.

Jellyport does not migrate resume positions, play counts, playback dates, favorites, ratings/likes, playlists, profile images or Emby account preferences. Mid-episode and mid-movie progress is unsupported. Existing destination values for those fields are left untouched, and no source playlist or profile-image reads are needed. Jellyfin role/template defaults for new accounts remain available independently of migration.

API clients may omit `migration_scope` or send `"watched_only"`. The legacy `"complete"` value is accepted for compatibility with older clients and persisted jobs, but is normalized to `"watched_only"` and cannot request a broader transfer. Unknown or non-string values are rejected. Previews and results report the normalized played-state scope.

Both live and saved-history sources use reusable matching metadata. Live source state is obtained through bounded explicit-ID batches; saved sources use the indexed private projection and retain only played playable items for transfer. Each account's destination candidates are checked through fresh user-scoped reads, including accessible items with no prior personal state. No user's permissions or activity are reused for another account.

## What can move

| Data | Behavior and limitations |
| --- | --- |
| Played / unplayed | Set matched playable items played when Emby has played them. Source unplayed never clears destination played state. |
| Episode completion | Transfer each matched episode's played flag. Jellyfin derives season/series completion from the episodes it contains. |
| Next Up / future seasons | Episode played flags can help Jellyfin select an unwatched episode. Original playback dates are not imported, so Next Up eligibility, ordering and persistence cannot be reproduced exactly. |
| Continue Watching | Not migrated. Existing Jellyfin progress remains untouched. |
| Resume, counts, dates, favorites, ratings, playlists, Emby preferences and images | Not migrated or synchronized. Existing destination values remain untouched. |

The item-data write is `POST /UserItems/{itemId}/UserData?userId={userId}` with only `Played: true`. Jellyfin's partial-field API preserves fields omitted from the request. The checked contracts are the [item controller](https://github.com/jellyfin/jellyfin/blob/v12.2/Jellyfin.Api/Controllers/ItemsController.cs), [update DTO](https://github.com/jellyfin/jellyfin/blob/v12.2/MediaBrowser.Model/Dto/UpdateUserItemDataDto.cs) and [user-data manager](https://github.com/jellyfin/jellyfin/blob/v12.2/Emby.Server.Implementations/Library/UserDataManager.cs).

## Jellyfin compatibility and preservation

Migration requires the modern partial-field user-data API available in supported Jellyfin **10.9+** versions. If it is unavailable, the migration stops rather than using the legacy watched-item endpoint: that endpoint can change counts, dates or resume state as a side effect. A successful write response is followed by independent played-state readback. Missing, mismatched or unsupported played values make the result partial rather than claiming success.

## Membership account slots

One Discord membership may own up to three independent Jellyfin account slots. Membership provisioning migrates each slot's matching Emby account, or its explicitly approved user mapping, separately. A slot without a matching source starts fresh; the primary account's history is not copied into its additional accounts. Defaults come from the selected Jellyport role or legacy template. Tier downgrades disable excess slots while retaining all their data, and later upgrades restore the same Jellyport-disabled accounts. Existing installations keep their original links as slot 1. See [membership allowances](../README.md#one-membership-with-several-accounts) for configuration and lifecycle behavior.

## Jellyfin onboarding roles

Account roles supply destination defaults independently of Emby migration. Import supported settings from an enabled, non-administrator Jellyfin account into a new or existing role. The encrypted snapshot is bound to the linked Jellyfin server and no longer depends on the source account after saving. The wizard can finish without a legacy template; choose a default role or template before creating or migrating accounts.

Roles separate permissions, account configuration, and shared server-backed home/display preferences. Home settings include the ten supported Home-row slots and their order, hidden rows, explicit default selections, horizontal/vertical TV layout, library landing pages, episode images, and skip intervals. These are destination Jellyfin settings captured from a Jellyfin user, not an import of Emby's arbitrary display-preference dictionary. They are stored in the shared account preference namespace used by Web and compatible TV/mobile apps. Each client renders the shared settings according to its capabilities; device-local options remain local. Unknown fields and unsupported values are excluded and reported.

Home copying reads and updates `DisplayPreferences/usersettings` with the legacy `client=emby` namespace used by Jellyfin Web and compatible clients. It merges the captured allowlist with a fresh destination read, preserving unrelated target settings. Blank Home-row selections are intentional defaults and are retained rather than dropped, so they can replace an older destination choice. The `tvhome` setting preserves the source's default, horizontal, or vertical layout. Existing saved roles need a new **Copy settings** and **Replace saved role** to capture these additions in 0.6.1.

The shared Home scope is visible in [Android TV's user settings](https://github.com/jellyfin/jellyfin-androidtv/blob/master/app/src/main/java/org/jellyfin/androidtv/preference/UserSettingPreferences.kt) and [Jellyfin Web's Home settings](https://github.com/jellyfin/jellyfin-web/blob/master/src/components/homeScreenSettings/homeScreenSettings.js). Library ordering, Home visibility, Latest Media exclusions, and hiding played items are already copied in the role's **Account preferences** group. Select that group as well as **Home and display preferences** for a complete Home update. Separate per-library client browsing preferences are not part of the shared Home snapshot. Next Up age cutoffs and rewatching controls are explicitly local in the checked [Web settings implementation](https://github.com/jellyfin/jellyfin-web/blob/master/src/scripts/settings/userSettings.js) and cannot be changed through this server-backed copy.

[Roku also reads the shared Home preferences](https://github.com/jellyfin/jellyfin-roku/blob/master/source/utils/session.bs), but the inspected client uses only the first eight row slots, adjusts unsupported/duplicate rows, and allows a local layout override. Copying all ten server slots preserves the source settings for clients that support them; it does not force every app to render an identical screen.

The default role applies only to newly provisioned accounts; no Emby preferences are imported. Existing destination accounts retain their settings during migration. To change them, assign a role explicitly, choose the setting groups, and review/apply an update for up to 100 eligible accounts. Each account has one Jellyport role; saving a role or assigning it alone causes no remote settings change. Passwords and personal media history remain intact during a role update.

Role application status records successful application of a saved revision, including partial setting-group results. It does not monitor live configuration drift or prevent users from subsequently changing permitted preferences. See [the role workflow](../README.md#account-roles-and-defaults) for creating defaults and updating existing accounts.

## Shows awaiting a future season

Suppose a user finished season 2 in Emby and season 3 is not yet in Jellyfin. Jellyport transfers matched episodes' played flags and leaves future episodes unplayed. Once season 3 is available and scanned, Jellyfin can identify its first unwatched episode.

This does not guarantee a permanent Next Up tile. Jellyfin applies playback-date cutoffs, library exclusions, special-episode settings and client display choices. Jellyport does not copy dates or manufacture activity to force a tile onto the home screen. Continue Watching positions and watch order are outside the migration scope. See Jellyfin's [Next Up implementation](https://github.com/jellyfin/jellyfin/blob/v12.2/Emby.Server.Implementations/TV/TVSeriesManager.cs).

## Data outside the migration scope

| Data | Treatment |
| --- | --- |
| Resume positions, counts, playback dates, favorites, likes/ratings and playlists | Not copied. Preserve existing Jellyfin data. |
| Passwords, PINs, login tokens, sessions, device authentication and Emby Connect links | Never imported. Generate new Jellyfin account passwords. |
| Emby permissions, configuration, profile images and client preferences | Not imported. Use a destination Jellyfin role or legacy template for new-account defaults, and the separate reviewed role-update workflow for existing accounts. |
| Full playback events, device/IP details and plugin statistics | Outside the played-flag adapter. |
| Library metadata, artwork, collection membership, media files, subtitles, analysis and DVR schedules | Not moved by an account migration. Both servers need their own media library. |
| Unsupported, unavailable or deleted media | No target is guessed; report eligible unmatched or unsupported history. |

## Reviewing a migration

Preview before a bulk migration. Every preview checks identities, mappings and protected destinations without catalog scans, history decryption or playlist reads. A saved-snapshot preview also validates the backup's server binding, user identity, original age and generation, and pins the generation shown for approval. Both modes return `history_deferred: true` and `stats: null`; exact history counts and matching details are deferred until approved execution. The actual migration matches played items, writes only the required played flags and independently verifies them. It reports unmatched/ambiguous media, failed writes and verification limitations. Existing unrelated destination state remains untouched. Any production verification or trial migration requires separate approval; API and client behavior can differ even when a request succeeds.

Reviews run as asynchronous, read-only tasks. The interface shows completed-account progress and polls once per second rather than waiting for one long HTTP response. Reviews can be canceled, have a 15-minute deadline, and retain completed results for 10 minutes. Results are private to the administrator session, held only in memory, and cleared on sign-out, restart or a configuration change. Rerun a cleared or expired review before approving a migration. At most two tasks run and sixteen are retained across the installation. Neither live nor saved-snapshot reviews start a background catalog crawl or wait for the migration history lock.

Each user's saved migration result includes at most 200 unmatched items and 200 ambiguous items, with at most 20 candidate matches per ambiguous item. Summary statistics count all eligible matching work. Previews return deferred statistics rather than zero counts and empty matching-detail lists until execution. These bounds limit browser-response size and persisted diagnostics; migration matching and its result counts still cover all eligible items. A completed preview larger than 8 MiB is rejected with a request to select fewer users.

For a new account using a saved role, the role's library restrictions determine which candidates are available after account creation. Execution verifies media through the newly created account's actual access and reports unavailable matches. A neutral catalog entry alone never authorizes a history write.

Approved migrations reuse a user-neutral Jellyfin catalog and identity index across the bulk job. Candidate selection includes every provider, series/episode-number and exact mapped-path hit for eligible played history, plus required parent series. It retains lower-priority and contradictory candidates until account access is checked. Each account reads fresh metadata and state through explicit `Ids` batches of at most 100 IDs and 6,000 encoded characters, without recursive enumeration, name sorting or total counts. Empty returned state remains eligible; omitted IDs are unavailable. Final matching uses the returned account-scoped items. A changed cached identity or preparation failure clears destination reuse and stops the remaining batch, rather than falling back to a full per-user catalog scan.

The in-process destination cache is bound to URL, API key, server ID and version, with ten-minute reuse after a successful build and one pinned catalog per job. Its capture timestamp still records when collection began. Live source migrations separately use a ten-minute metadata cache measured from collection start and read each user's source state fresh by explicit catalog IDs, retaining only played playable items. No cached source or destination personal state crosses account boundaries. Cold destination collection uses documented `SortName`, at most 100 items per page, disabled counts, `CollapseBoxSetItems=false`, and an empty page as the stopping condition. Disabling collection collapsing prevents a supported Jellyfin query path from enumerating the whole recursive library before pagination. It can remain slow on a large or busy server, but is performed once for a bulk job. The live catalog is not atomic: concurrent library edits or additions after collection can require a new migration.

Source migration reads have one active admission, at most eight waiting callers, and at least 500 ms idle after completion. A two-second response, five-second deadline, network/server rejection or cancellation of an active request opens a five-minute cooldown; longer bounded Retry-After hints extend it. Queued work is rejected rather than automatically retried or resumed. Limits include 100-item source pages and state batches, 200,000/64 MiB retained catalog items, and 100,000/32 MiB personal-state items. These are serialized-payload budgets, not exact JavaScript heap/RSS bounds. Source preparation failure stops the remaining batch instead of rebuilding a failed catalog for every account. See [performance safety](performance-safety.md) for verified Emby behavior and remaining risks.

Canceling a queued migration removes its encrypted request/settings record. Canceling active work aborts its clients and waits for in-flight item workers to drain; already-applied changes are preserved and remaining work requires review. A changed server URL or API key invalidates queued settings before remote work and stops running work at its next connection guard. The upstream may continue an already accepted request after cancellation; client abort is not proof of server-side completion.

Before a detailed item update, Jellyport refreshes the destination item's user data and recalculates the merge. The upstream API has no conditional update transaction, so concurrent playback during the brief read/write interval can still race with a migration. Run a user's migration while they are not actively watching for the most reliable result. Jobs explicitly report partial results and preserve ordinary existing account credentials and permissions.

## Saved Emby source snapshots — 0.12.0

Saved history can also come from [verified Emby plugin backups](emby-plugin-backups.md)
in Jellyport 0.14.0+. The original backup date determines freshness, and incomplete,
expired or changed input never triggers a live history fallback. Supported upgraded
database schemas are validated explicitly. Unmapped state types, orphan history and unusable display names produce aggregate
warnings while valid played history remains eligible. No target is guessed for missing catalog identities.

Without a configured plugin-backup source, live API reads remain the default. Plugin-backed migrations default to saved history; an unknown configured source requires an explicit choice. An optional helper on the same Linux Docker host as Emby captures library history once for all users rather than exporting each user's catalog through the API. It builds a new SQLite database containing only allowlisted migration columns from `MediaItems` and `UserDatas`, with only supported fields retained from metadata payloads. Unrelated native tables, sync targets/jobs, unused columns and arbitrary metadata are excluded. Only the encrypted projection reaches Jellyport; it is not a full Emby restoration backup. Migration uses its matching metadata and played flags only. Existing projections containing broader allowlisted state remain readable, but that state is not eligible for transfer.

Set `JELLYPORT_SNAPSHOT_METHOD=file_copy` on the helper for ordinary best-effort live-file copies; the helper Compose example selects this mode. It copies only `library.db`, `users.db` and available WAL files into helper-private work space. It does not copy `-shm` or authentication databases and makes no SQLite queries against the live source. SQLite performs normal WAL recovery, integrity checks and schema validation on the private copies before projection. No ZFS, downtime, backup plugin or special storage is required. These copies are not atomic: structural integrity does not prove semantic completeness or that all recent history was captured. Jellyport does not run `.recover` or accept salvaged/repaired data. Omitting the method preserves `sqlite_online_backup`, which captures a consistent library view through a pinned source read transaction. Capture metadata identifies `source_type: file_copy`; records without a method are treated as legacy Online Backup.

Saved-history migration validates current source identity without requesting Emby preferences, profile images or playlists. The snapshot cannot provide played activity recorded after its capture. Jellyfin's shared neutral catalog, fresh account candidate reads, access controls and pre-write checks remain live, preserving existing destination activity.

The adapter targets Emby 4.10.1.0 and validates its supported schema. Legacy file-copy and Online Backup helpers check mounted `device.txt` and `lastversion.txt` against the configured API server before and after capture. Plugin imports instead validate the backup manifest and `data/device.txt` as described in the [plugin guide](emby-plugin-backups.md). Only allowlisted user ID/GUID fields from `users.db` associate library history. File-copy and plugin modes read those fields from private copied databases, which can contain other sensitive account data and are never published; Online Backup uses the source identity adapter. No method copies `authentication.db` or Emby's configuration directory. Unknown schemas or unresolved identities are refused rather than inferred from usernames or internal numeric IDs. The isolated helper has a read-only source mount and no network; the web/API container has no Emby source or helper-work mount. See [deployment instructions](docker-deployment.md#optional-local-emby-snapshots--0120).

Both capture methods use CPU and storage bandwidth and have a five-minute worker deadline for capture and projection. File-copy mode avoids source SQLite queries and a pinned source read transaction, but still competes for disk bandwidth and can produce incomplete or unusable captures during writes. Online Backup pins a consistent library view; WAL writers can continue, while checkpoint/reset can be delayed and WAL size can grow until the reader closes. The deadline bounds the worker's duration, not WAL size. A failed, busy or unsupported capture retains the last good snapshot without switching to live history reads. Neither method provides a transaction across the library, identity database and live identity checks. [SQLite Online Backup](https://sqlite.org/c3ref/backup_finish.html), [WAL concurrency](https://sqlite.org/wal.html#concurrency)

Capture/import scheduling is disabled by default and uses the explicitly configured timezone. Administrators can request a capture/import and review its method/status without waiting for the copy in one HTTP request. Retained history is encrypted; status and preview expose bounded metadata, not raw databases. Raw library/users/WAL copies and the temporary projection stay in helper-only `/work` and are removed after capture. Jellyport never receives that mount or those raw files. Authenticated execution temporarily decrypts only the published projection in the private exchange directory. Active jobs retain that projection through destination writes until completion, failure or cancellation; previews no longer decrypt history. Failed removals remain tracked and block new decryptions until cleanup succeeds. Temporary-file cleanup does not guarantee forensic erasure or remove copies captured by host backups. Both private directories need restricted ownership and the exchange needs the same backup protection as Jellyport's data directory.

The web preview defaults to saved history for plugin-backed sources; legacy capture setups default to live reads, and an unknown configured source requires an explicit choice. Saved history requires a suitable snapshot for every selected user, with original history date and generation shown for approval. A database capture can retain broader allowlisted library state for schema compatibility, but migration consumes only matching metadata and played flags. The approved `source_snapshot_ids` map must cover exactly the selected source users. Missing, incompatible, changed, or older-than-48-hour snapshots fail closed; there is no automatic fallback to a live scan. Capture failure does not erase a usable last good generation. Clearing snapshots is refused while capture is running or an active job needs a pinned generation. After a failed or interrupted migration, review the snapshot's freshness again before approving a rerun.

Retention keeps the two latest encrypted projections, plus generations pinned by recent previews or queued/running jobs, up to eight generations. Preview pins last 30 minutes. New capture requests are refused when retained pins fill that limit. File-copy mode limits the combined source databases/WAL files to 8 GiB; Online Backup limits its source library database to 8 GiB. Published projections are limited to 8 GiB; a user's offline result is bounded to 100,000 items with personal state and 32 MiB. Exceeding a bound produces an error instead of a truncated migration. The helper work directory needs space for both raw capture and projection; temporary projection decryption needs additional exchange space beyond retained encrypted copies.

## Migration throughput and live progress — 0.11.3

The Jobs view reports the current account, its processing phase, matched items checked, and items updated. User accounts remain serialized. Up to four different destination items within the current account can be processed concurrently; matches targeting the same Jellyfin item stay in source order. A snapshot that already contains the merged state is skipped without an extra user-data read or write. A possible detailed update requires fresh destination user data before recalculating the patch, preserving newer Jellyfin playback activity. The four workers are drained before a fatal cancellation or guard error is returned, so account mutation locks are not released while those workers are still writing.

Destination catalog pagination disables total counts on every page and reads until an empty page, retaining repeated-ID detection and the supported size bound. The neutral index is shared across the job; each account's played-state matching uses an index over its fresh accessible candidates. Catalog pages have a 30-second deadline without automatic retries, 100 ms of cancelable idle time between pages, and a 15-minute deadline for the complete build. Partial builds are discarded. Emby's separate five-second source limit remains unchanged. Candidate reads have a normal 30-second deadline and at most three attempts for HTTP 429/503, with retry delays capped at two seconds. Reads remain sequential. Destination catalogs and retained candidate results are each limited to 200,000 items and 64 MiB of serialized data, with additional memory used by indexes and runtime objects. Jobs show shared-index preparation separately from account history, with accepted page/item counts and last-page latency. Aggregate preparation logs include page latency, item totals, read operations, cancellation/failure and cache hits without credentials, account/item identifiers or playback details. Only played playable items are eligible for transfer. Live target user data and permissions are not reused across accounts; unrelated state is never written.

Progress checkpoints are observational. Counters are persisted periodically, so an abrupt shutdown can leave the last displayed count behind changes already accepted by Jellyfin. This does not add automatic resumption from a per-item cursor: jobs that had never started can resume after restart, while running jobs become interrupted and require review. An approved rerun merges the remaining state using fresh destination activity. Account creation now saves its uncertainty record before sending the create request, so a crash before the response is recorded still requires inspection instead of blind replay. Legacy playlist journals remain stored for compatibility and review; new played-state migrations do not create or replay playlist copies. A missing progress increment does not authorize blind creation or replay.

The destination-worker changes have fixture and local-container coverage, not a production benchmark. One earlier synthetic run with 200 independent items and a 5 ms delay for each read and write took 2,248 ms sequentially and 562 ms with four workers. This demonstrates overlapping fixture waits, not measured media-server performance or a guaranteed fourfold speedup. Cold catalog reads, conservative idle intervals, database performance, library size, personal history, media-server load and network latency still affect duration. The 0.13.0 source defaults favor playback protection over throughput; production checks require separate approval.

## Troubleshooting a migration review

If a generic **502 Bad Gateway** appears before history matching can be reviewed, inspect the failed request in the browser's Network panel. An HTML gateway page or a plain status without Jellyport's JSON error can come from the reverse proxy when it cannot reach Jellyport or times out waiting. It does not establish that the Emby API key or user history is invalid. Check Jellyport container health and proxy connectivity. Background reviews now return a task ID promptly and use short polling requests, avoiding the previous long catalog request. Real upstream failures still appear as sanitized JSON errors or a failed review with a readable reason. Keep credentials and raw upstream responses out of shared logs or screenshots.

Both live and saved-snapshot reviews defer catalog matching, so a long review suggests connection, account-validation or snapshot-metadata trouble rather than an expected library crawl. Wait for progress or cancel an unwanted review. A review timeout, restart, sign-out or configuration change requires a new preview; the review causes no media-account writes. The approved job's cold destination catalog can still take time; inspect aggregate preparation logs for page counts and latency. A source-read cooldown stops approved work and requires review rather than automatic resumption. Do not repeatedly start reviews or migrations during the cooldown.

If the destination is your selected legacy template user, Jellyport rejects it before scanning history. The template is a source of permissions and preferences, and cannot also be a migration destination. Select a different destination account. If you need that account's settings without retaining it as a protected template, copy its supported settings into an **Account role**, choose that role as the default, and remove the legacy template selection before reviewing an otherwise eligible destination. Existing-account migrations retain their permissions and preferences; apply a role separately when you intend to change them.
