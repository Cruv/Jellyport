# Emby to Jellyfin migration capabilities

Jellyport migrates user records through the servers' authenticated APIs. Both servers must already contain the media. It does not copy media files or either server's database. Exact usernames are the default; an administrator-approved identity mapping can associate accounts with different names.

The default Complete merge preserves existing Jellyfin activity. Watched and favorite flags are combined, play counts use the larger value, and valid last-played dates use the later date. Confident matching is required; missing and ambiguous media are reported instead of guessed. Existing Jellyfin passwords, permission policies, and preferences remain intact. New accounts receive a generated password and the configured default account role, or the legacy Jellyfin template when no default role is selected.

## Choose a migration scope

**Complete** is the default and includes every supported data type in the table below. **Watched only** is an optional faster pass for played status. It considers watched playable source items and marks confident destination matches played. With the modern user-data API, when an item is newly marked played, it also includes its valid original last-played date if the destination has no date or an older date. Already watched destination items remain unchanged. This supports Jellyfin's episode-history basis for Next Up while preserving newer destination dates.

Watched-only mode does not transfer resume positions, play counts, favorites, ratings/likes, playlists, profile images, or source preferences. The modern partial-field user-data API preserves those unrelated destination values; the legacy fallback caveat below applies when it is unavailable. New-account role/template defaults and password generation work normally. Watched-only source queries can use Emby's [documented `IsPlayed=true` filter](https://dev.emby.media/reference/RestAPI/ItemsService/getUsersByUseridItems.html) for playable items; series identity is still read as needed for episode matching. Destination catalogs retain user scoping and are not filtered by watched status. Complete mode continues reading the full supported source state, including unplayed favorites, ratings, dislikes, progress, counts, and dates.

The selected scope is explicit in the preview and queued job. Review again after changing it. API clients use `migration_scope: "complete"` or `"watched_only"` on both preview and migration POST requests; omitting it preserves Complete behavior. Both scopes benefit from bounded concurrent item transfer, while watched-only mode additionally avoids unrelated data reads and writes. A later Complete pass can add the skipped supported data through the ordinary conservative merge.

## What can move

| Data | Migration behavior and limitations |
| --- | --- |
| Played / unplayed | Merge played flags for matched playable items. Emby's unplayed flag never erases a Jellyfin played flag. Fresh accounts retain unplayed defaults for untouched items. |
| Play count | Preserve the larger valid count, rather than adding counts and duplicating history on reruns. |
| Last played | Preserve the later valid timestamp through Jellyfin 10.9+ user-data updates. Emby's additional `UserDataLastPlayedDate` and `UserDataPlayCount` fields are requested where supported. Older Jellyfin watched endpoints may record the current date when no source date exists; this is reported. |
| Resume position | Copy a valid source position when the destination has no competing activity or the source activity is demonstrably newer. Preserve the destination when chronology is tied or unknown. Positions are not transferred beyond the destination item's duration. |
| Favorites | Merge favorites on confidently matched items, including series, seasons, albums, artists, books, photos, and collections when those records are exposed and identifiable on both servers. A favorite remains a favorite. |
| Personal likes and ratings | Copy valid personal values into empty destination fields. Preserve existing Jellyfin choices because preference changes have no reliable individual timestamps. `Likes` is copied only when the source actually supplies it; Emby's published DTO does not promise this field. Community/critic ratings are library metadata and are not user ratings. |
| Continue Watching | Jellyfin rebuilds the row from migrated resume positions, dates, playable items, and its own resume thresholds and client settings. Tile order and exact appearance can differ. |
| Next Up / future seasons | Migrate individual episode watched flags and available dates. Jellyfin then selects the next unwatched episode, including episodes from a new season after they are scanned. There is no permanent cross-server "follow this show" record to import. See the explanation below. |
| Playlists | Recreate user-visible playlists as private copies owned by the destination user. Match each member separately and retain supported order. Merge available playlist favorites/likes/ratings after confirming the copy. Missing members are reported. Existing unrelated Jellyfin playlists are preserved. Original public visibility, collaborators, description/artwork, and edit permissions are not copied. |
| Repeated playlist entries | Jellyfin 12 supports repeated entries. Jellyfin 10.9–10.11 removes duplicates during playlist insertion; migration must report that limitation rather than claiming an exact copy. |
| Portable playback preferences | For newly created accounts using a legacy template, copy an explicit allowlist of shared audio/subtitle language, subtitle mode, autoplay, remembered track selection, missing-episode display, and hide-played preferences over the template configuration. A configured default account role takes precedence: its preferences are preserved instead of overwritten by Emby preferences. Existing users keep their Jellyfin preferences. |
| Profile image | For newly created accounts, transfer a bounded PNG/JPEG profile image from the configured Emby server's user-image endpoint. Request a small image, validate its signature, and preserve existing Jellyfin profiles. No image URL from upstream metadata is fetched. |

The portable item-data write contract is `POST /UserItems/{itemId}/UserData?userId={userId}`. Jellyfin persists `Played`, `PlaybackPositionTicks`, `PlayCount`, `LastPlayedDate`, `IsFavorite`, `Likes`, and `Rating` when supplied. Although its update DTO also declares `PlayedPercentage`, `UnplayedItemCount`, `Key`, and `ItemId`, these are not independent values that Jellyport should import: percentages and aggregate counts are derived, while keys and IDs belong to the destination server. These behaviors were checked against Jellyfin's [item controller](https://github.com/jellyfin/jellyfin/blob/v12.2/Jellyfin.Api/Controllers/ItemsController.cs), [update DTO](https://github.com/jellyfin/jellyfin/blob/v12.2/MediaBrowser.Model/Dto/UpdateUserItemDataDto.cs), and [user-data manager](https://github.com/jellyfin/jellyfin/blob/v10.11.10/Emby.Server.Implementations/Library/UserDataManager.cs).

## Membership account slots

One Discord membership may own up to three independent Jellyfin account slots. Membership provisioning migrates each slot's matching Emby account, or its explicitly approved user mapping, separately. A slot without a matching source starts fresh; the primary account's history is not copied into its additional accounts. Defaults come from the selected Jellyport role or legacy template. Tier downgrades disable excess slots while retaining all their data, and later upgrades restore the same Jellyport-disabled accounts. Existing installations keep their original links as slot 1. See [membership allowances](../README.md#one-membership-with-several-accounts) for configuration and lifecycle behavior.

## Jellyfin onboarding roles

Account roles supply destination defaults independently of Emby migration. Import supported settings from an enabled, non-administrator Jellyfin account into a new or existing role. The encrypted snapshot is bound to the linked Jellyfin server and no longer depends on the source account after saving. The wizard can finish without a legacy template; choose a default role or template before creating or migrating accounts.

Roles separate permissions, account configuration, and shared server-backed home/display preferences. Home settings include the ten supported Home-row slots and their order, hidden rows, explicit default selections, horizontal/vertical TV layout, library landing pages, episode images, and skip intervals. These are destination Jellyfin settings captured from a Jellyfin user, not an import of Emby's arbitrary display-preference dictionary. They are stored in the shared account preference namespace used by Web and compatible TV/mobile apps. Each client renders the shared settings according to its capabilities; device-local options remain local. Unknown fields and unsupported values are excluded and reported.

Home copying reads and updates `DisplayPreferences/usersettings` with the legacy `client=emby` namespace used by Jellyfin Web and compatible clients. It merges the captured allowlist with a fresh destination read, preserving unrelated target settings. Blank Home-row selections are intentional defaults and are retained rather than dropped, so they can replace an older destination choice. The `tvhome` setting preserves the source's default, horizontal, or vertical layout. Existing saved roles need a new **Copy settings** and **Replace saved role** to capture these additions in 0.6.1.

The shared Home scope is visible in [Android TV's user settings](https://github.com/jellyfin/jellyfin-androidtv/blob/master/app/src/main/java/org/jellyfin/androidtv/preference/UserSettingPreferences.kt) and [Jellyfin Web's Home settings](https://github.com/jellyfin/jellyfin-web/blob/master/src/components/homeScreenSettings/homeScreenSettings.js). Library ordering, Home visibility, Latest Media exclusions, and hiding played items are already copied in the role's **Account preferences** group. Select that group as well as **Home and display preferences** for a complete Home update. Separate per-library client browsing preferences are not part of the shared Home snapshot. Next Up age cutoffs and rewatching controls are explicitly local in the checked [Web settings implementation](https://github.com/jellyfin/jellyfin-web/blob/master/src/scripts/settings/userSettings.js) and cannot be changed through this server-backed copy.

[Roku also reads the shared Home preferences](https://github.com/jellyfin/jellyfin-roku/blob/master/source/utils/session.bs), but the inspected client uses only the first eight row slots, adjusts unsupported/duplicate rows, and allows a local layout override. Copying all ten server slots preserves the source settings for clients that support them; it does not force every app to render an identical screen.

The default role applies only to newly provisioned accounts and takes precedence over portable Emby playback preferences. Existing destination accounts retain their settings during migration. To change them, assign a role explicitly, choose the setting groups, and review/apply an update for up to 100 eligible accounts. Each account has one Jellyport role; saving a role or assigning it alone causes no remote settings change. Passwords and personal media history remain intact during a role update.

Role application status records successful application of a saved revision, including partial setting-group results. It does not monitor live configuration drift or prevent users from subsequently changing permitted preferences. See [the role workflow](../README.md#account-roles-and-defaults) for creating defaults and updating existing accounts.

## Shows awaiting a future season

Suppose a user finished season 2 in Emby and season 3 is not yet in Jellyfin. Jellyport transfers the matched episodes' watched state and original last-played dates. It leaves future episodes unplayed. Once season 3 is available and scanned, Jellyfin can select its first unwatched episode for Next Up.

This is derived behavior, not a guarantee that a show remains visible indefinitely while no new episode exists. Jellyfin applies the client's Next Up date cutoff, library exclusions, special-episode settings, and other display choices. Old or missing source dates can affect eligibility. Jellyport does not manufacture recent activity to force a tile onto the home screen. Favorited series also remain available in Favorites.

The server selects eligible series from episode activity and then determines the next episode; it does not require a copied "series completed" flag. Copying aggregate season/series completion would be misleading when the libraries contain different episodes. See Jellyfin's [Next Up implementation](https://github.com/jellyfin/jellyfin/blob/v12.2/Emby.Server.Implementations/TV/TVSeriesManager.cs) and the [episode activity selection](https://github.com/jellyfin/jellyfin/blob/v10.11.10/Jellyfin.Server.Implementations/Item/BaseItemRepository.cs).

## Playlist safety and compatibility

Private playlist creation and direct user-data updates require Jellyfin **10.9 or later**. Jellyfin 10.8 lacks the checked update route and explicit private-playlist creation field. Unsupported or unknown capabilities must produce a warning; Jellyport must not fall back to a public playlist.

On older servers, or when the detailed user-data API is unsupported, played-status updates fall back to the legacy watched-item endpoint. That endpoint can also change derived play counts, resume positions, or playback dates. Watched-only mode sends no explicit resume, count, favorite, or rating fields, but cannot prevent those legacy server side effects. Strict partial-field preservation, including retaining a newer destination date or unrelated resume position, requires the modern user-data API. Jellyport reports a compatibility warning when using this fallback.

Creation uses `POST /Playlists` with the destination `UserId`, explicit `IsPublic: false`, and no shared users. Entry readback specifies the destination user. Ordinary API-key access does not provide a safe owner context for every playlist delete/reorder/share route, so migration preserves existing playlists instead of rewriting their membership. Source playlists shared with a user become that user's private copy, not a new public or shared resource. See the [playlist controller](https://github.com/jellyfin/jellyfin/blob/v12.2/Jellyfin.Api/Controllers/PlaylistsController.cs) and [create request](https://github.com/jellyfin/jellyfin/blob/v10.9.0/Jellyfin.Api/Models/PlaylistDtos/CreatePlaylistDto.cs).

The destination's insertion behavior matters: [Jellyfin 10.11 deduplicates members](https://github.com/jellyfin/jellyfin/blob/v10.11.10/Emby.Server.Implementations/Playlists/PlaylistManager.cs), whereas [Jellyfin 12 retains repeated entries](https://github.com/jellyfin/jellyfin/blob/v12.2/Emby.Server.Implementations/Playlists/PlaylistManager.cs). Jellyport creates each copy with its full matched entry list and private visibility in one request, then verifies ordered readback. Names include an `Emby import` suffix with a unique identifier. The encrypted journal binds each import to both servers and user IDs.

Reruns never append to an imported playlist: its owner may have made it public or shared since creation, and ordinary API-key access cannot safely prove its current sharing state across supported versions. An unchanged copy is recognized; source changes, destination edits, incomplete readback, or an uncertain creation are reported for manual review. A timed-out creation is never blindly repeated. This favors privacy and duplicate prevention over automatic playlist synchronization. Read-only confirmation can finish a previously created copy when its complete contents match.

Reads are bounded to 500 source playlists and 100,000 total entries per user. A single private creation is limited to 100,000 matched entries and a 4 MiB request body. Exceeding a limit produces a partial result instead of silently claiming a complete migration.

## Data without a safe automatic equivalent

| Data | Reason / achievable alternative |
| --- | --- |
| Passwords, PINs, login tokens, sessions, device authentication, Emby Connect links | Authentication systems are different. Generate new Jellyfin passwords; never import these secrets. |
| Emby permission policies and library-access IDs | Use a server-scoped Jellyfin account role or the optional legacy Jellyfin template. Emby IDs and privilege flags must not override destination access controls. |
| Every historical playback event, watch duration, device, IP, plugin statistics | Core item data exposes a count and latest date, not the full event ledger. Playback-reporting, Trakt, or other plugin data requires a separate explicitly supported integration. |
| Hidden-from-resume state | Emby has a hide endpoint, but its published readable user-data DTO does not expose a portable hide field, and the checked Jellyfin update DTO has no matching write field. Do not erase legitimate resume positions to approximate hiding. |
| Emby client themes, home layouts, sorting, device-local settings | Display preferences are scoped by client and item IDs, with no general export of all clients. Blindly copying Emby custom preference dictionaries can retain invalid IDs or change security-sensitive behavior. A Jellyfin account role can supply supported destination Web home/display defaults; it cannot migrate every Emby client or device-local setting. |
| Server-specific ordered views, excluded library IDs, local-password switches, profile PINs, cast receiver IDs | These are deliberately excluded from the portable configuration allowlist. |
| Emby intro-skip mode, rewind seconds, unsupported subtitle modes | The checked Jellyfin user-configuration model has no exact shared field or enum value. Client/plugin capabilities differ. |
| Smart playlist rules, external URLs, unsupported media, deleted or unavailable items | Copy only confidently matched destination library members. Dynamic rules and remote sources need a separate compatible feature; report unavailable members. |
| Library metadata, posters, collection membership, subtitles, intro/chapter analysis, DVR schedules | These belong to the library/server or another integration, not an account's portable user data. A favorite on an existing matched collection can move; creating or changing the shared collection cannot be inferred safely from a user migration. |

Configuration compatibility was checked against [Emby's user configuration](https://dev.emby.media/reference/RestAPI/UserService/getUsersById.html) and [Jellyfin's configuration model](https://github.com/jellyfin/jellyfin/blob/v12.2/MediaBrowser.Model/Configuration/UserConfiguration.cs). Display-preference scoping is documented by [Emby](https://dev.emby.media/reference/RestAPI/DisplayPreferencesService/getDisplaypreferencesById.html) and implemented by [Jellyfin](https://github.com/jellyfin/jellyfin/blob/v12.2/Jellyfin.Api/Controllers/DisplayPreferencesController.cs). Emby's [hide-from-resume contract](https://dev.emby.media/reference/RestAPI/UserLibraryService/postUsersByUseridItemsByIdHidefromresume.html) documents the write-only migration gap above.

Profile-image uploads use the authenticated user-image route and a base64 body, as implemented by Jellyfin's [image controller](https://github.com/jellyfin/jellyfin/blob/v12.2/Jellyfin.Api/Controllers/ImageController.cs). They do not import image URLs, arbitrary files, or SVG markup.

## Reviewing a migration

Preview before a bulk migration. Review unmatched and ambiguous media, unsupported capabilities, and missing dates. Newer or uncertain destination resume positions are retained automatically. The preview counts accessible source playlists from their metadata; it does not read playlist entries or verify their individual matches. The actual migration reads those entries, creates private copies, verifies their contents, and reports playlist differences or limitations. Test one representative account against the actual Emby/Jellyfin versions first: API and client behavior can differ even when a request succeeds.

History matching runs as an asynchronous, read-only task. The interface shows completed-account progress and polls once per second rather than waiting for one long HTTP response. It can be cancelled. A scan has a 15-minute deadline; completed results are retained for 10 minutes. Results are private to the administrator session, held only in memory, and cleared on sign-out, restart, or a configuration change. Rerun a cleared or expired review before approving a migration. At most two scans run concurrently and sixteen tasks are retained across the installation.

Each user's preview and saved migration result include at most 200 unmatched items and 200 ambiguous items, with at most 20 candidate matches per ambiguous item. The summary statistics still count the full catalog scan. These bounds limit browser-response size, retained review data, and persisted diagnostics; migration matching and its result counts still cover all eligible items. A completed preview larger than 8 MiB is rejected with a request to select fewer users.

For a new account using a saved role, preview matching uses the server catalog because no live template account is required. The role's library restrictions can reduce the final matched set. The execution phase reads media through the newly created account's actual access and reports unavailable matches; the preview warns about this difference.

New destinations within a single preview reuse one sanitized default template or server catalog, with personal state removed before reuse. Existing destinations always receive their own user-scoped catalog read. This cache lives only inside that preview; it is not shared with another preview or used for actual migration, which reads the created account's permitted catalog.

Before a detailed item update, Jellyport refreshes the destination item's user data and recalculates the merge. The upstream API has no conditional update transaction, so concurrent playback during the brief read/write interval can still race with a migration. Run a user's migration while they are not actively watching for the most reliable result. Jobs explicitly report partial results and preserve ordinary existing account credentials and permissions.

## Saved Emby source snapshots — 0.12.0

Live API reads remain the default. An optional helper on the same Linux Docker host as Emby can use SQLite Online Backup to capture `library.db` privately while Emby is running. It then builds a new SQLite database containing only allowlisted migration columns from `MediaItems` and `UserDatas`, with only supported fields retained from metadata payloads. Unrelated native tables, sync targets/jobs, unused columns, and arbitrary metadata are excluded. Only the encrypted projection reaches Jellyport; this is not a full Emby restoration backup. The snapshot supplies item metadata used for matching and each source user's played flags, original playback dates, counts, resume positions, favorites, and supported ratings/likes. Both Complete and Watched-only migration can use that history, without repeating a full live Emby catalog read for each migration. Snapshot collection captures the library once; it does not export every user's catalog through the API.

Complete mode continues to obtain source user identity/configuration, profile images, and playlist metadata and entries through live Emby API requests. These reads have their existing size bounds; extensive playlists can still require substantial work. Watched-only mode validates current source identity but does not request those extras. The snapshot cannot provide activity recorded after its capture, and these live extras are not transactionally aligned with it. Jellyfin target catalogs, access controls, and pre-write personal-state reads remain live in either mode, preserving the existing merge rules for newer destination activity.

The initial adapter targets Emby 4.10.1.0 and validates its supported schema. The helper checks the mounted server identity in `device.txt` and version in `lastversion.txt` before and after capture against the Emby API connection. It reads only allowlisted user ID/GUID fields from `users.db` to associate library history; it does not copy that database, authentication databases, or Emby's configuration directory. Unknown schemas or unresolved identities are refused rather than inferred from usernames or internal numeric IDs. The isolated helper has read-only access to the source database directory and no network. Jellyport's web/API container has no Emby source mount. See [deployment instructions](docker-deployment.md#optional-local-emby-snapshots--0120).

Capture does not require a quiet period or the Emby backup plugin. It still reads database pages, writes an isolated copy, and uses CPU and storage bandwidth. A pinned read transaction provides one consistent library view; WAL writers can continue, while checkpoint/reset progress can be delayed and the WAL can grow until the reader closes. The five-minute deadline limits capture duration, not WAL size. A failed, busy, or unsupported capture retains the last good snapshot. A library snapshot plus identity reads from another database does not provide a transaction across both databases. [SQLite Online Backup](https://sqlite.org/c3ref/backup_finish.html), [WAL concurrency](https://sqlite.org/wal.html#concurrency)

Capture scheduling is disabled by default and uses the explicitly configured timezone. Administrators can request a capture and review its status without waiting for the whole copy in one HTTP request. Retained snapshot history is encrypted; status and preview expose only bounded metadata to authorized administrators, not raw database contents. The raw backup and temporary projection stay in the helper-only `/work` mount and are removed after capture. Jellyport never receives that mount or the raw database. Authenticated reads temporarily decrypt only the published projection in the private exchange directory; a completed decrypted projection may remain for up to a minute between reads. Temporary-file cleanup does not guarantee forensic erasure or remove copies captured by host backups. Both private directories need restricted ownership and the exchange needs the same backup protection as Jellyport's data directory.

Snapshot use is selected explicitly for a preview. It requires a suitable snapshot for every selected user, with capture time and generation shown for approval. A database capture contains library state for both migration scopes; the scope chosen for the capture schedule does not remove other library state from that database. The approved `source_snapshot_ids` map must cover exactly the selected source users. Missing, incompatible, changed, or older-than-48-hour snapshots fail closed; there is no automatic fallback to a live scan. Capture failure does not erase a usable last good generation. Clearing snapshots is refused while capture is running or an active job needs a pinned generation. After a failed or interrupted migration, review the snapshot's freshness again before approving a rerun.

Retention keeps the two latest encrypted projections, plus generations pinned by recent previews or queued/running jobs, up to eight generations. Preview pins last 30 minutes. New capture requests are refused when retained pins fill that limit. Each database is bounded to 8 GiB; a user's offline result is bounded to 100,000 items with personal state and 32 MiB. Exceeding a bound produces an error instead of a truncated migration. The helper work directory needs space for both raw capture and projection; temporary projection decryption needs additional exchange space beyond retained encrypted copies.

## Migration throughput and live progress — 0.11.3

The Jobs view reports the current account, its processing phase, matched items checked, and items updated. User accounts remain serialized. Up to four different destination items within the current account can be processed concurrently; matches targeting the same Jellyfin item stay in source order. A snapshot that already contains the merged state is skipped without an extra user-data read or write. A possible detailed update requires fresh destination user data before recalculating the patch, preserving newer Jellyfin playback activity. The four workers are drained before a fatal cancellation or guard error is returned, so account mutation locks are not released while those workers are still writing.

Library pagination requests a total only for the first page and ignores page-size or zero totals returned when counting is disabled on later pages. Without a usable first total, it reads until an empty page while retaining repeated-page detection and the supported size bound. Playlist matching builds destination identity indexes once per account rather than again for each playlist. With the default live source, Complete mode preserves full per-user source-state reads and full playlist-entry migration; watched-only mode deliberately narrows its source selection. Live target user data and permissions are not reused across accounts. Narrow played/favorite/resume filters are not applied to Complete mode because they would omit supported ratings, dislikes, playback counts, or history dates.

Progress checkpoints are observational. Counters are persisted periodically, so an abrupt shutdown can leave the last displayed count behind changes already accepted by Jellyfin. This does not add automatic resumption from a per-item cursor: jobs that had never started can resume after restart, while running jobs become interrupted and require review. An approved rerun merges the remaining state using fresh destination activity. Account creation now saves its uncertainty record before sending the create request, so a crash before the response is recorded still requires inspection instead of blind replay. Playlist uncertainty journals retain their immediate safety writes. A missing progress increment does not authorize blind creation or replay.

The performance changes have fixture and local-container coverage, not a production benchmark. One synthetic run with 200 independent items and a 5 ms delay for each read and write took 2,248 ms sequentially and 562 ms with four workers. This demonstrates overlapping fixture waits, not measured media-server performance or a guaranteed fourfold speedup. Full catalog reads, database performance, library size, personal history, media-server load, and network latency still affect duration; compare representative accounts on your own server before estimating a 100-user batch.

## Troubleshooting a migration review

If a generic **502 Bad Gateway** appears before history matching can be reviewed, inspect the failed request in the browser's Network panel. An HTML gateway page or a plain status without Jellyport's JSON error can come from the reverse proxy when it cannot reach Jellyport or times out waiting. It does not establish that the Emby API key or user history is invalid. Check Jellyport container health and proxy connectivity. Background reviews now return a task ID promptly and use short polling requests, avoiding the previous long catalog request. Real upstream failures still appear as sanitized JSON errors or a failed review with a readable reason. Keep credentials and raw upstream responses out of shared logs or screenshots.

A large catalog can take time even with background matching. Wait for progress, cancel an unwanted review, or select fewer accounts for the next review. A timeout, restart, sign-out, or configuration change requires a new preview; it causes no media-account writes. Do not repeatedly start overlapping reviews while one is still running.

If the destination is your selected legacy template user, Jellyport rejects it before scanning history. The template is a source of permissions and preferences, and cannot also be a migration destination. Select a different destination account. If you need that account's settings without retaining it as a protected template, copy its supported settings into an **Account role**, choose that role as the default, and remove the legacy template selection before reviewing an otherwise eligible destination. Existing-account migrations retain their permissions and preferences; apply a role separately when you intend to change them.
